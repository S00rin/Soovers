# قابلیت‌ها و مرحلهٔ بعد

خواستهٔ مستقیم کاربر در این مرحله بر سند تحویل 0.3 مقدم بوده است: تمرکز آموزش، تعیین سطح و مسیر، تجهیزات قابل کاوش، سیستم دانشجو و مأموریت ATT&CK اجرا شده‌اند. سند قدیمی در `SOOVERS_CODEX_HANDOFF_FA.md` به‌عنوان سابقه نگه داشته شده؛ توصیف وضعیت جاری نیست.

| قابلیت | وضعیت 0.4 |
|---|---|
| برج، لابی، نقش و نمایش دسترسی | قابل اجرا؛ کارت‌های دمو در کلاینت |
| تعیین سطح و مسیر بر اساس حوزه | قابل اجرا؛ ارزیابی مقدماتی ۸ سؤال، نه آزمون صلاحیت حرفه‌ای |
| پنج درس، کاراکتر استاد، تخته و مرجع | قابل اجرا؛ درس‌های نوشته‌شده، بدون LLM یا استاد زنده |
| ذخیرهٔ مسیر، تکمیل درس و مأموریت | localStorage نسخه‌دار؛ حفظ دادهٔ دفترهای قبلی |
| pfSense و Suricata بازشونده، دنبال‌کردن بسته | مدل عملکردی آموزشی؛ هیچ دستگاه واقعی پیکربندی نمی‌شود |
| میز کار و فرمان‌های بررسی | مفسر محدود روی دادهٔ محلی؛ Shell و VM نیست |
| SOC و Tier 1/2/3 | فضای آموزشی و پروندهٔ مشترک؛ معماری واقعی سازمان‌ها می‌تواند متفاوت باشد |
| مأموریت ATT&CK و CTF | تصمیم‌های آموزشی قابل اجرا؛ دادهٔ ساختگی، امتیاز محلی |
| اتصال چند پروژهٔ واقعی به SOC | به Backend، هویت، مجوز پروژه و منبع لاگ نیاز دارد |
| هدست | مسیر WebXR قدیمی محفوظ؛ رابط آموزشی کامل و آزمون هدست باز است |

## ترتیب توسعهٔ بعدی

1. **هویت و ثبت پیشرفت سروری:** انتخاب سرویس هویت و پایگاه داده؛ اعمال مجوز سمت سرور، ذخیرهٔ Attempt و آزمون رد دسترسی. وابسته به زیرساخت شرکت.
2. **یک سیستم آزمایشگاهی واقعی:** Provider میز کار با نشست کوتاه‌عمر، مالک، شبکهٔ ایزوله، سقف منابع و پاک‌سازی. ابتدا یک سناریوی محدود Linux/Windows؛ پذیرش با دو نشست جدا و شواهد اجرای واقعی. هیچ Secret در کلاینت.
3. **SOC متصل:** یک پروژه و یک منبع SIEM، نرمال‌سازی رخداد، انتساب Tier و Audit. معیار پایان: همان رخدادِ تولیدشده در Lab در SOC دیده شود و تصمیم مجاز سمت سرور اعمال شود.
4. **VR هدف:** تعیین هدست، Teleport و کنترلر، UI قابل خواندن در صحنه، تعامل نشسته، توقف حرکت و اندازه‌گیری FPS. تکمیل دسکتاپ معادل این مرحله نیست.
5. **کلاس چندنفره:** Presence، اختیار استاد، تختهٔ مشترک و صوت، با آزمون دو کلاینت مستقل و بازاتصال.
6. **کاتالوگ تجهیزات:** افزودن مدل هر دستگاه با نسخهٔ سند و بررسی کارشناسی؛ نه استفاده از شکل یکسان با ادعای جزئیات سخت‌افزاری متفاوت.

مرزهای توسعه در `contracts.ts` مشخص‌اند. پیاده‌سازی یک Provider باید همراه Lifecycle، مجوز، timeout، وضعیت خطا، پاک‌سازی و تست باشد. افزودن یک عنوان به Interface به معنی فعال‌شدن سرویس نیست.
